# Epic: produce-perform-split

## Overview

The repo and the player serve two kinds of work that want different things:

- **Producing:** change the material. Lab boards, `verify`, loudness, `compare`, layout sheets, check-sounds, auto-perform
  design, and (soon) asking Claude to change a control (`llm-support`, PR 29). Heavy jobs, file writes, waiting is fine.
- **Performing:** play it. Live tracks, the controllers, auto-perform playback, visuals, rehearsals and gigs. The music
  must not drop out; nothing should write files or start a heavy job.

Today nothing says which is which. This epic finds out where the two really mix, and separates them where it pays off.

### What the survey found

The repo is mostly separated already. The mixing is in the player and in the track folders.

| Where | Today | Producing | Performing |
|---|---|---|---|
| `lab/`, `tools/`, `docs/` | own top-level folders | yes | no |
| `events/`, `TECH-STACK.md`, `superdirt-setup/` | own folders | no | yes (gigs, recording, hardware) |
| `tracks/<genre>/NNN-…/` | one folder holds the track, `-layout.pdf`, `.syx` (used on stage) **and** handovers, research, feedback, ideas (production history) | notes | track, sheet, `.syx` |
| Player track list | one dropdown: optgroups Live and Lab | Lab | Live |
| Player top bar and nav | Player, Tools, Analysis side by side | Tools, Analysis | Player |
| Tools page (`tools.mjs`) | check-sounds, loudness, layouts, stem-lab (2), set build: all one list, started from the same server that plays the music | all of them | none should run |
| Auto-perform | design (feedback loops, `perform/<track>/*.md`) and playback (script plays into the virtual port) | design | playback |
| Set 011 | generated by a tool; not in the player catalogue | build | play |

Findings:
1. **No folder move is needed for `lab/`, `tools/`, `events/`.** The top-level split exists.
2. **The player is the real mixing point:** one dropdown, one nav, and a Tools page that starts CPU-heavy jobs on the
   machine that is playing. On a 16 GB M2 a dense track can already drop out (`CLAUDE.md`, CPU rules).
3. **Track folders** mix stage artifacts with working notes. Moving notes changes paths cited in docs, skills and hooks;
   `npm run path-lint` finds them, but the gain is small. Decide last.

## Architecture Decisions

- **Two workspaces in the player, not two apps.** A `workspace` state, `produce` or `perform`, in `localStorage` and
  shown in the top bar. Same server, same engine, same page; the workspace only decides what is listed and what may run.
  Whether a third state "Rehearse" is needed is an open question; until answered, rehearsal belongs to Perform.
- **Perform lists what is played; Produce lists everything.** Perform: live tracks (and sets, see questions), the LC
  view, auto-perform playback, visual settings. Produce: Perform's list plus lab boards, Tools, Analysis, the Claude
  drawer (`llm-support`).
- **Perform refuses heavy and writing work, on the server.** The page tells the server its workspace (`POST /workspace`);
  `/run/*` and `/agent/*` return 423 while it is `perform`. A hidden button is not a guard; the server is.
- **Switching is deliberate.** Changing to Perform is one click. Changing to Produce while music plays asks for a
  confirm, so a stray click on stage does not open the Tools page.
- **Tag, do not restructure.** Catalogue entries and Tools commands get a `workspace` field (`produce`, `perform` or
  `both`), the single place that says which is which. The lists and guards read it.
- **Pre-show check lives in Produce.** A "Ready to perform" run (verify, sounds ok, layouts and `.syx` current,
  controllers found) is a Tools command that ends with a green or red line, so the heavy work happens before the set.
- **Track folders last.** If notes move, they go to `tracks/<genre>/NNN-…/notes/`; stage artifacts stay next to the
  track. Only after the player work shows it is worth the path churn.

## Technical Approach

### Server (`tools/trajectory/`)
- `workspace.mjs`: state (last value from the page), `POST /workspace`, `GET /workspace`; a helper `refuseIfPerform`
  used by `tools.mjs` and `agent.mjs`.
- `catalogue.mjs` and `tools.mjs`: add the `workspace` field; `toPublic` sends it.

### Page
- Top bar: workspace switch (Produce / Perform), nav entries filtered by workspace, the track dropdown filtered by it.
- A visible state: the Perform workspace is calm (no Tools link, no drawers that write), the Produce workspace shows
  its tools. Keys follow the workspace.
- Settings (visual) stay in both.

### Repo and docs
- `CLAUDE.md` "The player" and "Layout": one paragraph on the two workspaces and what belongs to each.
- Optional: notes folder move with `path-lint`.

## Risks

- **Two workspaces add a click.** For Jonas and Jojo on stage that is a cost. Mitigation: Perform is the default on
  load, and the switch remembers the last choice.
- **A guard in the wrong place.** The page filter alone can be bypassed or go stale. Mitigation: the server refuses,
  and the page shows the refusal.
- **Server state is stale.** The page crashes in Perform and the server stays locked. Mitigation: the lock expires
  without a page heartbeat (about 10 s) and falls back to open.
- **Moving folders breaks paths.** Mitigation: optional, last, `path-lint` before and after.
- **Over-design.** The repo is already mostly split. Mitigation: task 1 may end with "two small changes and stop".

## Open Questions

1. Two workspaces (Produce, Perform) or three (Produce, Rehearse, Perform)? Rehearsal may want Lab boards and some
   checks that a gig does not.
2. Are lab boards ever played, not only produced? A board is an instrument to try with the controllers; Perform could
   list them as "Boards" or leave them to Produce.
3. Set 011 is generated and is not in the catalogue. Should Perform list it? Then the catalogue needs a `set` kind.
4. Auto-perform: design in Produce, playback in Perform. Should Perform offer the script list only (no design files)?
5. Does Jojo want the split on his machine, or only Jonas?
6. Layout sheets and `.syx` are produced by a hook after every edit and used on stage (print, Novation Components).
   Should the pre-show check list them with their age?
7. Is moving track notes into `notes/` worth it at all?

## Success Criteria (Technical)

- Every catalogue entry and every Tools command has a `workspace` value; a check fails the build when one is missing.
- In Perform the dropdown lists no lab boards and the nav has no Tools / Analysis; in Produce both are there.
- With the page in Perform, `POST /run/<command>` gets 423; in Produce it works as before. With no page heartbeat for
  10 s the guard opens.
- Leaving Perform while a track plays asks for a confirm; nothing else asks.
- "Ready to perform" for 008 and 010 ends with one result line and the exit code of the worst check.
- `CLAUDE.md` names the two workspaces and what belongs to each; `npm run path-lint` is clean.
